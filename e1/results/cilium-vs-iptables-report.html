At 10,000 Services, iptables doubles request latency. Cilium doesn't move.

Comparing Service routing in Calico (iptables) and Cilium (eBPF) as a cluster grows from 100 to 10,000 Services.

36 benchmark runs on 28–29 September 2026. Each run: 200 requests per second over 4 connections for 30 seconds.

Why they behave differently

When a pod calls a Service, the kernel has to turn the Service's virtual IP into a real pod IP. Both setups store one entry per Service port (plus entries per backend), so both tables grow as you add Services. The difference is how the kernel finds the right entry.

iptables: walk the list

A new connection is checked against the KUBE-SERVICES chain rule by rule, top to bottom, until one matches. Add Services and the list gets longer.

Cost grows with the number of Services: O(n)

Cilium eBPF: jump straight to it

An eBPF program hashes the destination IP and port and does a single lookup in a BPF map. The map can hold ten or ten thousand Services; the lookup is the same.

Cost stays constant: O(1)

The slow tail follows the median

The 99th percentile is what the slowest 1 in 100 requests experiences. It's noisier than the median, so each run matters more here.

One honest detail: at smaller sizes iptables actually has the tighter tail (4.30 ms against Cilium's 5.27 ms at 2,080 Services, and 3.82 against 5.35 ms at 100). The lines cross around 6,000 Services. The eBPF advantage is about scale, not about every request being faster at any size.

A surprise: where the rule sits matters less than how many there are

If the cost were only the walk to the matching rule, a Service found near the top of the chain would be fast no matter how long the chain is. The benchmark recorded where the target Service landed in KUBE-SERVICES, so that can be checked.

So something beyond the walk to the match scales with the total ruleset. Likely candidates are the iptables backend in use (legacy or nft; iptables -V on a node tells you), rules in other chains that every new connection passes, and CPU cache pressure from a large ruleset. This benchmark can't separate them, but for the main question it doesn't need to: whatever the mechanism, the cost grows with the number of Services on iptables and not on Cilium.

Findings

Cilium's latency is independent of Service count. Median latency was 2.33 ms at 100 Services and 2.25 ms at 10,000. The fitted slope is −0.007 ms per 1,000 Services, which is run-to-run noise.
iptables adds about 0.23 ms per request for every 1,000 Services. Median latency rose from 2.36 ms to 4.74 ms, a 101% increase, and it fits a straight line almost perfectly (r = 0.995). That linear shape is the O(n) rule walk showing up in the data.
The gap opens immediately and keeps widening. The two are tied at 100 Services. By 2,080 Services iptables is 23% slower; by 10,000 it is 2.1× slower, 2.49 ms per request.
Lookup method, not table size, explains the difference. Cilium holding 50,146 entries (2.25 ms) beats iptables holding 44,710 rules (3.32 ms). Both tables grow linearly; only the linear search pays for it. The chart is in the appendix.
Tail latency confirms it, with a caveat at small scale. iptables p99 grew 94%, from 3.82 to 7.40 ms. Cilium's p99 ended lower than it started (5.35 to 4.80 ms) but varies more between runs, up to 4 ms apart at 4,060 Services.
Both were equally reliable at this load. All 216,000 requests succeeded and both setups held the 200 requests per second target in every run, so the difference is purely latency.

Within this setup, the data supports the claim. Cilium's eBPF datapath keeps Service routing cost constant as the cluster grows, while iptables cost grows linearly with the number of Services and doubled median latency by 10,000.

Limits of this benchmark

Three runs per point is enough to see a trend this strong, not to measure small effects. Only one load level (200 requests per second) was tested, so this says nothing yet about maximum throughput or node CPU usage. The latency includes the application's own response time of roughly 2.2 ms, which is why the absolute difference (2.49 ms) tells you more than the ratio. Rule update time, how long it takes to apply a change when a Service is added, wasn't measured, and that's another place where iptables is known to struggle at scale.

Appendix: table size isn't the problem, lookup is

If more entries alone made things slow, Cilium would suffer too: it programs about 5 entries per Service against iptables' 11 rules per Service, and at 10,000 Services it holds over 50,000 of them.
